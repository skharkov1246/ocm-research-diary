# Узел bench: протокол сравнения CPU и GPU

Узел платформы трека «Простая литая ГТУ-заменитель» (issue #59), пункт 5 задания «Расчёт промышленной газовой
турбины на AWS»: по каким измерениям решать, переносить ли ядро SU2 на CUDA и когда переходить к нескольким
узлам. Сам протокол — `PROTOCOL.md`.

Состояние на 14.11.2026: прогонов по протоколу не было, в облаке ничего не запускалось. Готовы протокол,
конфигурация, разбор журналов SU2 с тестами и порог окупаемости по тарифам us-east-1.

| файл | что это |
|---|---|
| `PROTOCOL.md` | что умеют SU2, OpenFOAM, CalculiX на GPU; задача бенчмарка; что мерить; допуски точности; правило решения; переход к нескольким узлам |
| `bench.toml` | задача, критерии сходимости, допуски, правила решения, 8 конфигураций; тестовые значения помечены EXAMPLE, с владельцем данных и влиянием на точность (`[[example_data]]`) |
| `bench_parse.py` | журналы SU2 (`history*.csv`, `*.log`, `nvidia-smi`, `nsys`, `/usr/bin/time -v`) → `bench_summary.csv` и сверка с эталоном `bench_compare.csv` |
| `break_even.py` | `tariffs` (Price List AWS + Spot Instance Advisor), `mesh` (узлы и рёбра сеток), `compute` → `break_even.json` |
| `tariffs_us-east-1.json` | тарифы us-east-1 и eu-north-1 от 14.11.2026 с sha256 исходных файлов |
| `mesh_stats.json` | узлы и рёбра сеток узла geom (core130 coarse/medium, taurus60 coarse) |
| `break_even.json` | порог S* по парам GPU × CPU × рынок, доля ядра по Амдалу, оценка видеопамяти и обмена, упор в полосу памяти, сверка с цифрами задания |
| `test_bench.py` | 19 тестов на придуманных журналах (SYNTHETIC) |
| `speed_su2.py` | замер на машине: с/итерацию канала SU2 (medium, fine) при разбиениях NPxK, время сетки, память → `speed_su2_<case>.json` |
| `speed_ccx.py` | замер на машине: колесо C3D10 в ccx — статика при 1/8/64 потоках, упаковка, частоты → `speed_ccx_<case>.json` |
| `speed_merge.py` | замеры задач прогона → `speed_aws_results.json`: цена точки SU2 medium/fine и расчёта ccx (формулы и допущения в файле) |
| `make_jobs_bench.py` → `jobs_aws_bench.json` | файл задач раннера: `bench-su2-c7a16`, `bench-su2-c7i16`, `bench-ccx-c7a16`, блоки `estimate`, `merge`, `plan_check` |
| `test_speed.py` | 8 тестов разбора и пересчёта цены на придуманных данных (SYNTHETIC) |

```bash
python3 -m pytest -q test_bench.py
python3 break_even.py compute --bench bench.toml --out break_even.json
python3 bench_parse.py --bench bench.toml --runs runs --out bench_summary.csv --compare bench_compare.csv
```

Папки прогонов `runs/` в репозиторий не идут (`.gitignore`); сводки CSV и обновлённый `break_even.json` после

## Замер скорости машин для сметы уровней 2–3 (AWS, подготовлено 15.11.2026, не запускалось)

Вопрос: сколько стоит одна рабочая точка SU2 на сетке medium и fine и один трёхмерный расчёт CalculiX на
c7a.16xlarge. Смета узла su2 (`../su2/jobs_aws_su2_kv3.json`) держится на C = 35,24 мкс·ядро на узел и итерацию с
общей 4-ядерной машины под нагрузкой и на допущении EFF = 0,8 — замер их заменяет. Сходимость здесь не меряется:
время до сходимости даёт протокол (раздел выше), он ждёт сошедшегося расчёта на CPU.

| задача `jobs_aws_bench.json` | что меряет | итог задачи |
|---|---|---|
| `bench-su2-c7a16` | с/итерацию канала core130: medium (584 357 узлов) при 64x1, 32x2, 16x4 и fine (уровень impeller.py) при 64x1, 32x2; 40 итераций первого порядка + 100 MUSCL; время сетки; память | `speed_su2_core130.json` |
| `bench-su2-c7i16` | то же на запасном типе раннера (64 vCPU = 32 ядра × 2 потока) | то же |
| `bench-ccx-c7a16` | колесо core130 C3D10 на 50/150/450 тыс. узлов: статика CENTRIF при 1/8/64 потоках, упаковка 8 × 8, частоты (10 форм) до 250 тыс. узлов | `speed_ccx_core130.json` |

Слияние: `speed_merge.py --in routes/gtu/platform/aws/runs/<run_id> --run-id <run_id> --out speed_aws_results.json` —
цена точки = итераций на точку (6000, как у узла su2) × с/итерацию лучшей конфигурации / K; база линии и сетка
концепции — отдельными строками; другое число узлов — пересчёт ∝ узлам (помечен). Для ccx — дешёвый из «один
расчёт на всю машину» и «упаковка»; разброс max|U| между числами потоков (`max_disp_rel_spread`) — сверка, что
многопоточный SPOOLES дал то же решение (у `../fea/disk.py` однажды 4 потока дали невязку равновесия 1,6 %).

- `mpirun` идёт с `--use-hwthread-cpus`: OpenMPI 4.1 считает слоты по физическим ядрам, у c7i.16xlarge их 32 при 64
  vCPU, и `-np 64` без ключа отказывает («not enough slots» — проверено локально: на 4 ядрах `-np 5` отказ).
  То же касается задач узла su2 с 64 процессами при откате на c7i.16xlarge.
- Смета (блок `estimate`): ожидаемо 2,54 долл. за три машины, верхняя граница раннера 7,40 долл.; модель времени
  и источники — там же. Скрипты сами держат срок задачи (`--job-max-min`): что не успевает, пропускается с пометкой.

максимально разных вариантов. Весь счёт идёт на AWS. Локально (4 общих ядра) — только тесты и короткие пробы.

`funnel_budget.json` (`make_jobs_l23.py`).

## 1. plan (без AWS)

```bash
for f in jobs_l0_debug jobs_l0 jobs_l1_debug jobs_l1 jobs_l1_fea jobs_l2 jobs_l3; do
  python3 routes/gtu/platform/aws/runner.py plan routes/gtu/funnel/$f.json --branch claude/lucid-allen-yvps5d \
      --assume-price 0.748 --assume-zone-prices us-east-1a=0.955,us-east-1b=0.748,us-east-1c=0.706; echo "$f: $?"; done
```

Ожидается код 0 у всех семи файлов (проверено 15.11.2026, поле `plan_check` в файлах). `plan` не проверяет, что файлы из
команд задач есть в ветке, и не запускает команды: это делает шаг 0 и локальная проверка на малом объёме (раздел 12). В выводе надо
прочитать:
- `[задача]` — образ al2023, Python 3.12 (uv) или контейнер, 64 vCPU, сторож;
- `[бюджет]` — «израсходовано + в работе + пакет + новая … из 2000 — можно»;
- `[зоны]` — самая дешёвая зона, us-east-1c.

Раннер v2 уже в ветке. Если до запуска его изменят, `plan` надо повторить. Файлы задач пересобираются командами
`make_jobs_l0.py`, `make_jobs_l1.py` и `make_jobs_l23.py`.

Раннер выполняет команду задачи как `bash cmd.sh` без `-e`: код выхода задачи — код последней строки. Поэтому в задачах уровня 1
код `funnel_l1.py` сохраняется и возвращается после списка частей (`rc=$?` … `exit $rc`). В задачах уровня 0 (уже посчитаны) этого
нет: упавший `funnel_l0.py` дал бы `exit_code: 0`, ловит только слияние (код 2). При повторе уровня 0 — сначала поправить
`make_jobs_l0.py` так же.

## 3. Слияние уровня 0 и отбор по нишам (сделан)

Отбор на уровень 1 — архив ниш (MAP-Elites). Ниша = архетип × роторы × компрессор × турбина × охлаждение × рекуператор ×
изготовление ротора. В отбор идут лучшие K из каждой допустимой ниши, общий топ-1000 и фронт Парето. K подбирается под цель
`--target 4000`.

KV-3: **3983 записи** (`l0_aws_full/funnel_l0_select_KV-3_n200000.json`):
- K = 7 на нишу;
- покрыты все 393 допустимые ниши; есть 8 почти допустимых из ниш без допустимых;
- по архетипам: безмасляный 1154, печатный рекуператор 772, RDC 605, печатный монолит 542, волновой ротор 329, гибрид 288,
  кластер 140, керамика 125, литой монолит 14, традиционная 7, простой ротор 7 (все 7 — почти допустимые).

Отладочный вход — `l0_aws_debug/funnel_l0_select_KV-3_n2000.json`: 307 записей, уровень 1 берёт из них 150.

Критерии прохода уровня 0 — `funnel_budget.json`, поле `criteria.L0`. Все выполнены: полнота, ниши сошлись, отбор покрывает
каждую допустимую нишу.

## 6. Первое слияние, затем CalculiX для лучших 300 — `jobs_l1_fea.json`

`<run_id>` ниже — прогон `jobs_l1.json`; `<run_id_fea>` — прогон `jobs_l1_fea.json`.

```bash
python3 routes/gtu/funnel/merge_l1.py --kv KV-3 --m 3983 --shards 40 --in routes/gtu/platform/aws/runs/<run_id> \
    --out-dir routes/gtu/funnel/aws/l1_full --suffix _KV-3_m3983 --fea-top 0 --compare-in routes/gtu/platform/aws/runs/<run_id> \
    --no-scale --fea-cases-out routes/gtu/funnel/aws/l1_full/funnel_l1_fea_cases.json
```

Это первое слияние: без масштабирования, поэтому быстро. Дальше:
1. `aws/l1_full/funnel_l1_fea_cases.json` — закоммитить и запушить.
2. `runner.py run routes/gtu/funnel/jobs_l1_fea.json --branch claude/lucid-allen-yvps5d --live`. Задача — контейнер
   `ubuntu:24.04` + `calculix-ccx`, `strength_l1.py --run-cases`, случаи `disk.py` идут параллельно на `$NPROC` (ccx — в один
   поток), сторож 40 мин.
3. Скачанный `runs/<run_id_fea>/l1-fea300/funnel_l1_fea_results.json` положить в `aws/l1_fea/`. Проверить `n` = числу случаев и
   поля `error`.

**Точка остановки 2 — сходимость.** Смотреть поля `starts_check` и `convergence` результатов.
- **По стартам.** Если у 10 % из 640 вариантов и больше оценка при 8 стартах отличается на 0,05 и больше
  (`improved_gt_0_05 + worse_gt_0_05` ≥ 64) или различаются `feasible_base` и `feasible_2x` — повторить полный уровень 1 с 8
  стартами. Смета ×2 по оптимизации: около 10 долл. ожидаемо, верхняя граница около 40.
- **По объёму.** Сравнить отбор 50 разных на M/2 и на M. Если общих ниш меньше 80 % или средняя оценка 50 разных меняется на
  0,05 и больше — нужен `merge_l0 --target 10000` по слитым частям уровня 0 (S3) и повтор уровня 1 на расширенном входе. Смета
  ×2,5: около 15 долл. ожидаемо, около 60 по верхней границе.
- Если всё сошлось — объём достаточен. Дальше не тратить.

## 7. Окончательное слияние и отбор 50 разных

```bash
python3 routes/gtu/funnel/merge_l1.py --kv KV-3 --m 3983 --shards 40 --in routes/gtu/platform/aws/runs/<run_id> \
    --out-dir routes/gtu/funnel/aws/l1_full --suffix _KV-3_m3983 --fea-top 0 --compare-in routes/gtu/platform/aws/runs/<run_id> \
    --fea-results routes/gtu/funnel/aws/l1_fea/funnel_l1_fea_results.json
```

Что делает это слияние:
- **Отсев по CalculiX до отбора.** Вариант, у которого `disk.py` дал запас по разрушающей частоте при 120 % ниже 1,0 хоть у
  одного колеса, становится недопустимым с причиной `fea_burst` (`merge_l1.apply_fea_results`, тест).
- **Жадный отбор 50.** Критерий — «оценка − 1,0·exp(−d/0,15)»: не больше 3 вариантов на нишу, ни одного ниже порога оценки 5,0.
  Обоснование порога — README, «Отбор 50 разных».
- **Цена разнообразия.** Средняя оценка 50 разных против чистого топ-50, число вытесненных, сколько мест хуже, наибольшая потеря
  места, чувствительность к λ.
- **Метрики разнообразия.** Число архетипов и ниш, среднее и минимальное попарное расстояние.
- **Масштабирование 50 на KV-1 и KV-6.** Повтор оптимизации на других точках (Saturn 20, Titan 130).

**Не решено: масштабирование считается не на AWS.** `merge_l1.py` повторяет оптимизацию 50 отобранных на KV-1 и KV-6
(100 вариантов × 4 старта) в своём процессе, то есть на машине сессии. Оценка по двум замерам задачи масштабирования с 2
стартами (проба: 291 с, `funnel_l1_results.json`, `timing.scale_s`; проверка файлов 15.11.2026: 230 с) × 2 по стартам × 100: около
13–16 ядро-часов, 3–4 ч на 4 ядрах. Это против решения
владельца (локально — не больше 12 вариантов и 2 стартов) и вне сметы уровня 1. Пока задачи AWS для масштабирования нет: либо
окончательное слияние запускается на машине AWS (задачей раннера, с частями из S3), либо `--no-scale` и масштабирование отдельной
задачей. До решения — не запускать окончательное слияние без `--no-scale` на 4 ядрах.

Выход в `aws/l1_full/`:
- `funnel_l1_results_KV-3_m3983.json`;
- `funnel_l1_KV-3_m3983.csv` (все варианты с причиной отсева);
- `funnel_l1_top50_KV-3_m3983.json` и `.csv`.

У каждого из 50 есть: архетип, схема, детали и узлы, модули замены, шаги монтажа, Plug&Play по 10 интерфейсам, тепловой КПД, габарит,
масса (оценка), TRL, ближайший сосед и чем от него отличается, поле `geometry` в метрах для эскизов с трёх ракурсов.

Если допустимых выше порога окажется меньше 50, итог — сколько есть, причины — в `reject_detail`. Это результат моделей, а не
нехватка объёма: после исправлений скептиков в пробе прошли 2 из 12.

Затем — вход уровня 2:

```bash
python3 routes/gtu/funnel/funnel_l2.py prepare --input routes/gtu/funnel/aws/l1_full/funnel_l1_top50_KV-3_m3983.json --top 50 \
    --out routes/gtu/funnel/aws/l2/l2_cases_KV-3.json
```

С ожидаемой стоимостью кода в ожидании (38,30 + 49,97) всё вместе ожидаемо — 640,6. Итог 552 включает израсходованные вне списков

По верхней границе всё вместе выходит на 55 долл. за потолок 2000. Ожидаемо — 552 долл. (28 % потолка), по плану — 1299. Поэтому
важен порядок запуска: предохранитель раннера останавливает новые машины, не давая превысить 2000.

**Порядок запуска воронки.** Приоритет владельца — уровни 0 и 1. Накопленная сумма — по верхней границе, от уже израсходованных
1,20:

1. L1 отладка — 3,1.
2. L1 полный + `l1-starts2x` — 26,5.
3. L1 CalculiX — 27,6.
4. L2 геометрия + прочность — 30,3.
5. L2 SU2 coarse, только после ворот — 196,5.
6. L3 SU2 medium, 5 вариантов — 448,6.

Пакеты камеры и SU2 KV-3 идут своими сессиями под тем же потолком.

**Точки остановки:**
1. **Предохранитель раннера.** Перед каждым запуском проверяется: израсходовано + в работе + новая ≤ 2000 долл. Это жёсткий стоп.
2. **Отчёт владельцу после каждых 500 долл.** общего расхода по журналу — `report_step` раннера, решение владельца 14.11.2026.
   Дальше — только после ответа. Уровни 0–1 этот порог не достигают. Его пересекут пакеты камеры и уровни 2–3.
3. **Уровни 0 + 1 — до 1500 долл.** (решение владельца). По смете это 26,7 по верхней границе.
4. После отладки уровня 1: фактическое время на вариант больше 2 × сметы — стоп и пересборка `make_jobs_l1.py` (раздел 4).
5. После полного уровня 1: сходимость не достигнута — повтор с 8 стартами или `--target 10000` (раздел 6). Каждый повтор —
   не больше 60 долл. по верхней границе.
6. **SU2 уровня 2 — только после ворот.** Перебор стратегий разгона (`platform/su2/jobs_aws_su2_kv3_sweep.json`) должен дать
   вердикт success. После двух первых задач `l2-su2-*` без линии частоты остальные 15 машин не запускать.
7. Уровень 2 прошли меньше 5 вариантов — уровень 3 не запускается.
8. Уровень 3 расширяется до 10 вариантов (`make_jobs_l23.py --l3-slots 10`, верхняя граница 504) только при достаточном запасе
   до 2000.

## 11. Уровни 2–3 (коротко; пока только план и файлы задач, без затрат)
